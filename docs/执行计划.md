# 好习惯 App 执行计划

> 依据：[产品规划](./产品规划.md)  
> 文档版本：1.0  
> 更新日期：2026-07-15  
> 当前状态：Android MVP 已完成代码实现、自动化测试和 APK 构建；下一阶段进入真机内测与反馈迭代

## 1. 计划目标

以 Android 为首发平台，完成一款离线优先、无需账号的习惯养成 MVP，并保证核心业务和界面结构能够快速扩展到 iOS。

首版交付的核心闭环为：

> 创建习惯 → 今日提醒 → 快速打卡 → 撤销或补记 → 查看回顾 → 调整或继续习惯

## 2. 默认决策

以下内容作为项目默认方向，除非用户测试或技术验证给出明确反证，否则不在每个阶段重复讨论：

| 项目 | 默认决策 |
| --- | --- |
| 产品气质 | 温和极简为主，数据分析为辅 |
| 首发平台 | Android |
| 跨平台技术 | Flutter |
| 首版账号 | 不需要账号 |
| 数据策略 | 离线优先，本地保存，可导出恢复 |
| 首版习惯类型 | 完成型 |
| 补记策略 | 允许历史补记并保留补记时间 |
| 游戏化 | 首版仅保留轻量反馈，不做 RPG |
| 视觉基础 | Material 3 + 自有温和极简设计令牌 |
| 主要参考设备 | 小米 15，同时覆盖中低端 Android 环境 |

## 4. M0：产品定义

### 4.1 工作项

- 固化产品定位、目标用户和首版范围
- 写清习惯、计划日期、记录、提醒、暂停和归档的业务关系
- 为每种打卡状态定义进入和退出条件
- 明确补记、撤销、休息、暂停和跨时区规则
- 定义首版统计口径
- 整理异常场景和用户可恢复方案
- 建立需求编号和版本变更记录

### 4.2 必须回答的问题

- 当天已完成后修改习惯计划，历史记录是否变化
- 删除习惯是永久删除还是默认归档
- 暂停期间是否允许用户主动补记
- 提醒跨过午夜后应归属哪一天
- 修改设备时间和时区后如何处理已有记录
- 数据恢复时遇到重复记录如何处理
- 未来同步是否需要兼容首版数据

### 4.3 交付物

- 产品规格说明
- 状态转换表
- 数据字段字典
- 异常场景清单
- MVP 需求清单与优先级

### 4.4 验收标准

- 产品、设计和开发可以对同一场景得到一致结果
- 所有 MVP 功能都能映射到明确的用户价值
- 所有非 MVP 功能已被记录，但不会进入首版开发

## 5. M1：交互原型与视觉系统

### 5.1 页面范围

- 首次启动与简短引导
- 今日页：空状态、部分完成、全部完成
- 快速创建习惯
- 完整创建与编辑习惯
- 习惯列表、排序、暂停和归档
- 习惯详情与历史日历
- 历史补记和撤销
- 回顾首页与近 30 天统计
- 提醒与外观设置
- 数据导出和恢复入口

### 5.2 设计任务

- 建立颜色、字体、间距、圆角、图标和阴影令牌
- 完成浅色、深色和高对比度方案
- 定义打卡状态的颜色与图形表达，不能只依赖颜色区分
- 建立习惯卡片、日期格、进度、按钮和提醒组件
- 设计完成、撤销、错误和空状态反馈
- 控制动效强度，并设计减少动态效果模式

### 5.3 原型测试任务

至少验证以下任务：

1. 新用户创建“每天晚上阅读”的习惯
2. 用户在今日页面完成打卡并撤销
3. 用户为前一天补记
4. 用户将习惯暂停一周后恢复
5. 用户查看最近 30 天完成率
6. 用户找到数据导出入口

### 5.4 验收标准

- 目标用户无需讲解即可完成六个测试任务
- 普通打卡不超过一次主要点击
- 创建简单习惯只需填写名称、频率和可选提醒
- 补记与当天打卡在视觉上可区分但不带惩罚感
- 大字体下主要操作仍可见、可点击且不重叠

## 6. M2：技术验证与工程准备

> 此阶段在用户确认进入开发后启动；本轮不执行。

### 6.1 技术验证主题

- Flutter 在目标 Android 版本上的基础运行和构建
- 本地数据库的数据迁移、事务与恢复能力
- 定时提醒在 HyperOS 和常见 Android 环境下的表现
- 后台限制、重启后提醒恢复和系统时间变化
- 跨时区日期归属规则
- 数据导出、导入和重复数据处理
- 深色模式、大字体和无障碍语义
- 未来 iOS、Widget 和健康平台能力的接口边界

### 6.2 架构产物

- 工程模块划分
- 数据模型与迁移策略
- 打卡事件和每日状态计算规则
- 平台能力适配接口
- 日志、崩溃和匿名指标策略
- 测试金字塔与自动化范围
- 第三方依赖与许可证清单

### 6.3 验收标准

- 不依赖网络即可完成核心闭环
- 杀死进程和重启设备后数据与提醒仍可恢复
- 日期、时区和夏令时场景有明确测试结论
- 技术选型没有阻止后续 iOS 扩展的结构性问题

## 7. M3：Android MVP 实现顺序

> 以下为未来编码阶段顺序，不表示当前已经开始开发。

### 7.1 第一增量：本地习惯管理

- 创建、编辑、排序和归档完成型习惯
- 每天和指定星期计划
- 今日应执行习惯计算
- 基础浅色与深色主题

**完成门槛：** 用户关闭并重开 App 后，习惯和顺序保持一致。

### 7.2 第二增量：打卡闭环

- 当天完成、撤销和备注
- 历史日历
- 补记、删除历史记录
- 休息和暂停
- 当前连续与完成率计算

**完成门槛：** 所有状态转换均有自动化测试，历史记录不会因编辑计划被意外改写。

### 7.3 第三增量：提醒

- 本地提醒
- 提醒开关和时间修改
- 稍后提醒
- 重启后的提醒恢复
- 通知权限引导

**完成门槛：** 小米 15 及至少一个中端 Android 环境完成通知测试记录。

### 7.4 第四增量：回顾与数据安全

- 月历状态
- 当前连续、历史最佳和近 30 天完成率
- 本地数据导出与恢复
- 错误提示和恢复路径

**完成门槛：** 使用导出文件可以在全新安装环境恢复核心数据。

### 7.5 第五增量：可访问性与体验收尾

- 大字体和显示缩放
- 屏幕阅读器语义
- 高对比度与减少动态效果
- 动效和触觉反馈
- 空状态、错误状态和加载状态

**完成门槛：** 核心流程仅使用屏幕阅读器也可以完成。

## 8. M4：稳定性内测

### 8.1 内测重点

- 连续使用 14 至 30 天的数据稳定性
- 通知到达与重复通知问题
- 跨午夜、跨时区和修改系统时间
- 进程被系统回收后的状态恢复
- 大量历史记录下的首页和日历性能
- 导出、清除和恢复数据
- 升级版本后的数据库迁移

### 8.2 建议测试矩阵

| 维度 | 覆盖 |
| --- | --- |
| 主要真机 | 小米 15 |
| 性能补充 | 至少一台中端或低端 Android 设备 |
| 屏幕 | 小屏、主流屏、大字体和显示缩放 |
| 外观 | 浅色、深色、高对比度 |
| 网络 | 离线、弱网；首版核心功能不应依赖网络 |
| 系统状态 | 省电、重启、应用升级、时间与时区变化 |

### 8.3 发布阻塞条件

出现以下任何一项时不得公开发布：

- 用户记录丢失或错误覆盖
- 提醒大量重复或无法关闭
- 补记导致历史日期错乱
- 升级后数据无法迁移
- 主流程崩溃或无法撤销误操作
- 隐私说明与实际数据行为不一致

## 9. M5：Android 首发准备

- 完成应用名称、图标、启动页和商店截图
- 编写隐私政策、数据导出和删除说明
- 整理第三方许可证声明
- 配置正式签名、版本策略和发布渠道
- 准备首发说明、常见问题和反馈入口
- 建立崩溃、通知和数据恢复的支持流程
- 完成发布前回归测试

首版发布后优先观察创建成功率、首次打卡率、第 2/7/30 天留存、通知到达率、数据恢复成功率和用户主动暂停/恢复情况。

## 10. M6：iOS 扩展

### 10.1 前置条件

- Android MVP 的业务模型和数据规则已经稳定
- 有可用的 macOS、Xcode 和 iOS 真机环境
- 关键第三方依赖均确认支持 iOS
- 设计已完成 iOS 导航、权限和系统组件适配

### 10.2 主要工作

- 复用习惯、计划、记录和统计业务逻辑
- 适配 iOS 通知、后台行为和系统权限
- 适配安全区域、手势返回和平台导航
- 验证数据导出、恢复和未来同步兼容性
- 使用符合许可要求的 iOS 图标和系统交互
- 完成 App Store 隐私与发布材料

### 10.3 验收标准

- Android 与 iOS 对同一记录数据计算出相同状态和统计结果
- iOS 操作符合平台习惯，不机械复制 Android 导航
- 无账号和离线模式在 iOS 上同样完整可用

## 11. MVP 验收场景

首版至少通过以下端到端场景：

1. 新用户在无网络环境创建一个每日习惯并完成打卡
2. 创建一个仅周一、周三、周五执行的习惯
3. 当天打卡后立即撤销，统计恢复正确
4. 为过去某天补记，日历和完成率更新正确
5. 暂停习惯后，暂停日期不计入失败
6. 修改习惯名称和提醒，不改写历史记录
7. 归档习惯后，历史数据仍可查看
8. 修改设备时区后，历史记录归属日期不被静默重写
9. 重启设备后提醒仍按计划工作
10. 导出数据，清空环境后恢复，习惯和记录保持一致
11. 深色模式与大字体下完成所有核心操作
12. 使用屏幕阅读器完成创建和打卡

### V1.1：记录能力增强

- 计数型和时长型习惯

### V1.2：专注与例程

- 专注结果关联习惯

### V1.3：同步与 iOS

- 可选账号与云端备份

### V2：生态与智能能力

- Health Connect、Apple Health 和穿戴设备

## 13. 项目风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 提醒在不同 Android 系统上不稳定 | 用户错过计划 | 早期做真机验证，提供系统设置引导和应用内状态检查 |
| 补记、暂停和计划修改规则过于复杂 | 数据统计矛盾 | 在编码前完成状态表与端到端测试用例 |
| 首版功能膨胀 | 延迟核心闭环 | 新功能默认进入后续功能池，必须用用户价值证明才能进入 MVP |
| 只在旗舰机测试 | 中低端体验差 | 增加低性能与小屏测试基线 |
| 过度追求跨平台一致 | iOS 体验不自然 | 共享业务和设计令牌，平台导航与权限分别适配 |
| 未来同步破坏本地数据 | 丢失或重复记录 | 首版预留稳定 ID、修改时间、删除标记和数据版本 |
| 开源资源许可证不兼容 | 商业和发布风险 | 建立第三方资产清单，引用前逐项复核许可证 |

## 14. 当前阶段的下一步

在不写代码的前提下，下一轮建议依次完成：

1. 输出 MVP 详细需求清单和状态转换表
2. 绘制“今日、创建习惯、历史补记、回顾”四条核心流程
3. 制作低保真线框图
4. 确定品牌名称、主色和图标风格
5. 制作可点击原型并进行首轮用户测试
6. 根据测试结果冻结 MVP 规格
7. 用户确认进入开发后，再启动 M2 技术验证与工程搭建

## 15. 进度维护规则

- 每个里程碑只有在交付物和验收标准同时满足后才能完成
- 新增需求必须标注所属版本，不得默认加入当前里程碑
- 所有产品规则修改需同步更新产品规划、测试场景和数据规则
- 每次公开发布前都要执行数据迁移、通知、补记和恢复回归测试
- 本计划中的时间安排应在团队规模和经验明确后再转换成日历排期
